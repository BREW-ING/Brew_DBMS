# Brew — Build Specification

> **Full title:** Brew – A Real-World Signal-Driven Hackathon & Project Idea Recommender
> **Purpose of this file:** This is the single source of truth for an AI coding agent (Antigravity, Codex, etc.) building this project. Follow it phase by phase, in order. Do not skip ahead to a later phase before the current phase's files exist and work. Do not invent folder structure not listed here — ask/pause instead of guessing.

---

## 1. What We're Building (one paragraph)

Brew continuously pulls real-world "problem signals" from GitHub, arXiv, news, and Reddit, embeds them into a vector database, and matches them against a user's skills, team size, and time budget to recommend hackathon/side-project ideas that are actually feasible — not generic AI-hallucinated ideas. It also uses a graph database to recommend teammates whose skills complement the user's own. Three database paradigms are used deliberately: PostgreSQL (structured data), a vector database (semantic matching), and Neo4j (relationship/graph matching).

---

## 2. Non-Goals (do not build these)

- Do NOT generate ideas from a generative model with no grounding — every suggestion must trace back to a real ingested signal (a GitHub issue, arXiv abstract, news article, or Reddit post).
- Do NOT build a full social network / chat feature for teammate matching in v1 — just the recommendation list.
- Do NOT hardcode API keys anywhere in source files. All secrets live in `.env.local` (frontend) or `.env` (ingestion service), both git-ignored.

---

## 3. Tech Stack

| Layer | Choice |
|---|---|
| Frontend | Next.js (App Router) + TypeScript + Tailwind CSS |
| Design system | Notion-style via `npx getdesign@latest add notion` (see Section 8) |
| Auth | NextAuth.js — two roles: `user`, `curator` |
| SQL database | PostgreSQL (Supabase or Neon) |
| Vector database | pgvector (extension on the same Postgres) — fallback option: Qdrant Cloud |
| Graph database | Neo4j AuraDB (free tier) |
| Ingestion / embedding service | Python (FastAPI) — separate service, not Next.js API routes, because scraping + embedding libraries are far better supported in Python |
| Scheduling | GitHub Actions scheduled workflows (cron) |
| Hosting | Vercel (frontend), Railway or Render (Python ingestion service) |

---

## 4. High-Level Architecture

```
 [GitHub Actions cron] ──triggers──▶ [Python ingestion service]
                                            │
                                            ▼
                                   [PostgreSQL: problem_signals]
                                            │
                                (embedding job, separate step)
                                            ▼
                                   [Vector DB: signal embeddings]
                                            │
      [Next.js app] ──user request──▶ [Matching Engine] ◀── [Neo4j: teammate graph]
                                            │
                                            ▼
                                 [Feasibility Scorer] ──▶ [Suggestions returned to user]
```

## 6. Build Phases — Follow In Order

**Do not start Phase (n+1) until Phase n produces a file that runs / renders without errors.**

### Phase 0 — Scaffolding
1. Create the folder structure above (empty files where noted).
2. `.gitignore` must exclude: `.env`, `.env.local`, `node_modules/`, `__pycache__/`, `.venv/`.
3. Root `README.md`: project title, one-paragraph description, link to `docs/ARCHITECTURE.md`.

### Phase 1 — Database schema (no app code yet)
1. Write `db/postgres/schema.sql` with tables: `users`, `skills`, `user_skills`, `constraints`, `problem_signals`, `suggestions`, `feedback`, `ingestion_sources`.
2. Write `db/neo4j/constraints_and_seed.cypher` with node labels `User`, `Skill`, `Interest` and relationships `HAS_SKILL`, `INTERESTED_IN`, `COLLABORATED_WITH`.
3. Do not proceed until both scripts run cleanly against a fresh local/dev database.

### Phase 2 — Ingestion service (Python, standalone, no frontend dependency)
1. Build `services/ingestion/common/schema.py` first — the shared normalized signal shape everything else depends on.
2. Build **one adapter only** to start: `github_adapter.py`. Get it fetching + normalizing + inserting into Postgres end-to-end before touching the other three adapters.
3. Only after GitHub works: build `arxiv_adapter.py`, `news_adapter.py`, `reddit_adapter.py` the same way, one at a time.
4. Build `jobs/embed_signals.py` last in this phase — it depends on signals already existing in Postgres.

### Phase 3 — Frontend skeleton (no real data yet, use mock data)
1. Run the design system installer (Section 8) before writing any component.
2. Build `app/layout.tsx`, `nav-bar.tsx`, and the `(dashboard)` route group with mock/hardcoded suggestion data first — validate the UI shell works before wiring real APIs.
3. Build `(auth)` pages and NextAuth config — two roles (`user`, `curator`) must exist before the `(curator)` routes are role-guarded.

### Phase 4 — Wire frontend to real data
1. `lib/db.ts`, `lib/vector.ts`, `lib/neo4j.ts` — one connection helper at a time, test each independently (e.g. a throwaway script or API route that just logs a query result) before using it inside a page.
2. `api/suggestions/route.ts` — connects matching engine (vector search + Postgres constraints).
3. `api/teammates/route.ts` — connects Neo4j query layer.
4. Replace mock data in dashboard pages with real API calls, one page at a time.

### Phase 5 — Advanced DB features
1. Triggers (stale-signal expiry), stored procedures (feasibility scoring), materialized view (trending problem areas) — add these to `db/postgres/schema.sql` and a new migration file, not by hand-editing a live database.

### Phase 6 — Scheduling + deployment
1. `.github/workflows/ingest.yml` and `embed.yml` — wire these last, after the underlying scripts are proven to work when run manually.
2. Deploy frontend to Vercel, ingestion service to Railway/Render.

## 7. API Keys & Environment Variables — Step-By-Step

**Do not write any code that assumes a key exists before this step is reached in the relevant phase.** When you (the AI agent) reach a point where a real API key is needed, stop and output a message telling the human exactly which key to obtain and where to put it — do not fabricate a placeholder value and continue as if it were real.

### `apps/web/.env.local` (create from `.env.local.example`)
```
DATABASE_URL=              # Postgres connection string (Supabase/Neon)
NEXTAUTH_SECRET=           # generate with: openssl rand -base64 32
NEXTAUTH_URL=http://localhost:3000
NEO4J_URI=
NEO4J_USER=
NEO4J_PASSWORD=
VECTOR_DB_URL=             # only if using Qdrant separately from Postgres
```

### `services/ingestion/.env` (create from `.env.example`)
```
DATABASE_URL=
GITHUB_TOKEN=              # GitHub personal access token (repo scope not needed, public read only)
NEWSAPI_KEY=                # or GDELT — GDELT needs no key
REDDIT_CLIENT_ID=
REDDIT_CLIENT_SECRET=
REDDIT_USER_AGENT=
EMBEDDING_MODEL=            # e.g. "all-MiniLM-L6-v2" (local, free) or "text-embedding-3-small" (hosted)
EMBEDDING_API_KEY=          # only needed if using a hosted embedding model
```

**When each key becomes relevant:**
- `DATABASE_URL` → needed starting Phase 1, before any schema script runs.
- `GITHUB_TOKEN` → needed at the start of Phase 2, step 2.
- `NEWSAPI_KEY`, `REDDIT_CLIENT_ID/SECRET` → needed only when building those specific adapters — not before.
- `NEXTAUTH_SECRET`, `NEO4J_URI/USER/PASSWORD` → needed starting Phase 3, step 3 and Phase 4.
- `EMBEDDING_API_KEY` → only needed if a hosted embedding model is chosen instead of a local one; ask the human which they want before assuming.

## 8. Design System — Notion-Style UI

Before writing any component in Phase 3, run:

```bash
npx getdesign@latest add notion
```

from inside `apps/web/`. This installs a Notion-style component/design-token set into `components/ui/`. Do not hand-write buttons, cards, inputs, or typography styles before running this — use the generated components and tokens instead of ad hoc Tailwind classes, so the UI stays visually consistent across every page. Do not edit files inside `components/ui/` directly; wrap or compose them from the app-level components instead (`suggestion-card.tsx`, etc.).

## 9. Conventions

- TypeScript strict mode on. No `any` unless genuinely unavoidable (comment why).
- Every new Postgres schema change goes in `db/migrations/` as a new timestamped file — never edit `schema.sql` retroactively for a change that's already been "shipped" in a previous phase.
- Python: type hints on every function signature in `adapters/` and `jobs/`.
- Commit after each phase, not after each file — commit message format: `phase(N): short description`.
- If a decision in this spec seems wrong once you're actually building (e.g. a folder that doesn't fit), stop and flag it rather than silently deviating.

## 11. Reference — Database Paradigm Justification (for your report, not the agent)

- **PostgreSQL:** structured, relational data needing integrity and transactions — users, skills, constraints, ingestion sources, feedback.
- **Vector DB (pgvector):** problem signals and user profiles are unstructured text; semantic similarity search is not expressible in plain SQL.
- **Neo4j:** teammate compatibility is a network problem — skills, interests, and past collaborations form a graph, and "who complements this user" is a natural traversal query, not a join.
